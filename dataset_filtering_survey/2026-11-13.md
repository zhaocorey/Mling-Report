**功能描述**：

corpus-assay 专门回答一个问题：**我的训练数据中是否包含了即将报告的评测基准的文本？**

核心机制：
- 从评测基准（如 GSM8K、MMLU 等）构建哈希 n-gram 索引（默认 13-gram）
- 用多进程 Rust 扫描器流式处理 Parquet/JSONL 分片
- 当文档与基准共享 ≥ `min_hits` 个 distinct 13-gram 且覆盖率 ≥ `min_coverage` 时标记为污染
- 输出逐基准、逐分片、逐测试条目的归因报告
- 支持 `reproduce` 命令从 manifest 精确复现扫描结果

**技术亮点**：

| 特性 | 说明 |
|------|------|
| 性能 | 8 核 ~80k docs/s（~28 MB/s 文本），接近线性扩展 |
| 内存效率 | mmap 后端：1.6 GB 索引 + 8 worker 仅占 2.2 GB 峰值内存 |
| 短文本处理 | `--exact-channel` 对短题目（数学题、多选题）做精确匹配 |
| 可复现 | 索引和扫描记录 config hash、数据集 revision、工具版本 |
| 鲁棒归一化 | Unicode NFKC + 小写 + 停用词移除，抗大小写/标点/空格变化 |
| 实验性功能 | spaced-seed 通道可检测轻度编辑的近似副本 |

**与现有工具对比**：

| 工具 | 定位 | 语言 | 去污染方式 | 速度 | 归因粒度 |
|------|------|------|-----------|------|---------|
| **corpus-assay** | 基准去污染（专用） | Rust + Python | n-gram 哈希匹配 | ~80k docs/s (8核) | 逐测试条目 |
| Data-Juicer | 通用数据清洗 | Python | 规则+模型过滤，无专用基准去污染 | 中等 | 文档级 |

**corpus-assay 的独特价值**：它是目前**唯一**专注于"训练数据 vs 评测基准"污染检测的开源工程化工具，且具备：
1. 逐条目归因（告诉你具体哪道题泄露了）
2. 可复现审计（manifest + hash 校验）
3. Rust 级性能（比纯 Python 方案快一个数量级）

## 📊 趋势洞察

### 1. 数据去污染（Decontamination）方向的兴起

本次发现的 corpus-assay 指向一个正在形成的工程需求：**在训练前/训练中系统性检测并移除评测基准泄露**。

近期论文也印证了这一趋势：
- *"Are LLM Benchmarks Already Contaminated? A Systematic Review of Contamination Detection Methods"* — 综述化信号
- *"When Benchmarks Leak: Inference-Time Decontamination for LLMs (DeconIEP)"* — 推理时去污染
- *"Detecting Data Contamination from Reinforcement Learning Post-Training for LLMs"* — RL 后训练阶段的污染检测
- *"LLM Benchmark Datasets Should Be Contamination-Resistant"* — 从基准设计端防污染
- *"DAPT-Bench"* — 针对被污染数据的动态基准方案

**判断**：去污染正在从"事后检查"演变为"pipeline 内置环节"。corpus-assay 的工程成熟度（审计、复现、归因）表明社区开始将去污染视为**基础设施级能力**。

### 2. Rust 在数据处理工具链中的渗透

corpus-assay 采用 Rust 核心 + Python 接口的架构，延续了 datatrove、tokenizers 等工具的模式。Rust 在以下场景展现优势：
- **流式扫描**：大文件的零拷贝内存映射（mmap）
- **并行计算**：多进程 n-gram 匹配，无 GIL 瓶颈
- **内存安全**：大索引场景下的确定性内存占用

对于 TB 级预训练语料的去污染扫描，Rust 实现相比纯 Python 可获得 5-10x 加速。

### 3. 基准测试污染问题的关注度提升

污染问题正在多维度展开：
- **预训练阶段**：训练语料包含基准测试文本（corpus-assay 针对的场景）
- **后训练阶段**：RL/SFT 数据泄露（DeconIEP、RL 污染检测）
- **合成数据**：模型生成的训练数据可能间接包含基准内容（SynthSentry）
- **评估端**：推理时动态去污染（DeconIEP）

这对多语言数据集构建的启示：**多语言基准污染检测目前仍是空白**。corpus-assay 的 Unicode NFKC 归一化对多语言有一定支持，但其 n-gram 匹配本质上是单语逐字匹配，无法检测：
- 跨语言翻译污染（英文基准 → 中文训练数据的翻译泄露）
- 语义等价污染（改写、同义替换）

## 💡 建议

### 是否值得纳入 pipeline

**建议：值得关注，暂缓纳入。** 理由：

| 维度 | 评估 |
|------|------|
| 工程质量 | ✅ 高（Rust 核心、审计复现、归因报告完善） |
| 社区成熟度 | ❌ 极低（0 stars，创建仅 40 天） |
| 多语言适用性 | ⚠️ 有限（n-gram 匹配对多语言有效但不完整；无跨语言翻译检测） |
| 与我们 pipeline 的契合度 | ⚠️ 中等（我们目前无基准去污染环节，如需添加则它是唯一选择） |

**建议路径**：
1. 在 sandbox 环境中试用 corpus-assay 对现有训练语料做一次基准污染扫描（GSM8K、MMLU、HumanEval 等常用基准），了解当前污染基线
2. 如果扫描发现有意义的污染率（>0.1%），则将其纳入 pipeline 的"训练前质检"环节
3. 持续观察其社区发展（star 数、issue 活跃度、PyPI 下载量），等待 v0.3+ 稳定版

### 后续关注方向

1. **跨语言去污染**：这是一个明确的研究空白。如果英文基准被翻译成其他语言后混入训练数据，现有工具均无法检测。这可能是我们 pipeline 的差异化方向
2. **去污染 + 去重的联合 pipeline**：corpus-assay（基准去污染）+ datatrove/SemHash（文档去重）的组合方案
3. **corpus-assay 的 spaced-seed 通道**：实验性功能，可检测轻度编辑副本，如成熟则能覆盖更多污染场景
4. **SynthSentry 类工具**：检测训练数据中的合成数据污染（模型生成数据回流），这是另一个正在浮现的问题
